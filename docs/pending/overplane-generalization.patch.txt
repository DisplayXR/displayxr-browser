DEFERRED — the Windows generalization of the over-plane composite fix.
NOT A PATCH FILE. Do not put this in patches/ and do not `git am` it.

WHAT THIS IS
------------
These five hunks were split out of patches/0112 ("inline-3d(#119, #120): draw
mono from the scratch we own") before that patch was finalized. They are
preserved here VERBATIM — hunk headers and all, exactly as they were emitted by
`git format-patch` in the combined draft — so the follow-up that lands them does
not have to be re-derived from the argument.

The file lives in docs/pending/ with a .txt extension on purpose: it must not be
reachable by `git am patches/*.patch`, and applying it as-is would collide with
the Android arm's fix for the same function.

WHY IT WAS DEFERRED
-------------------
The Android arm shipped a device-verified fix for the SAME defect in the SAME
function, on the other `#if` arm — the over-plane occlusion composite hoisted out
from behind the five weave preconditions so it runs on weave-less frames too
(all five exits plus the healthy path). Landing this Windows twin alongside it
would put two competing implementations of one function into the tree, which is
the thing to avoid. So the Android fix goes first, and the WINDOWS
GENERALIZATION OF IT lands later as its own follow-up. This text is the input to
that follow-up, not a second implementation to merge beside it.

THE DEFECT, for whoever picks this up
-------------------------------------
Patch 0057 added `if (batch && !wove_this_frame) { ... return; }` before phase
(B), and it was RIGHT when written: phase (B) was then only the whole-window
woven draw-back, and blitting a woven texture that still holds the previous
page's pixels is the navigation ghost. Patch 0064 then put the Phase-2
OVER-PLANE COMPOSITE into phase (B) as well, and nobody revisited the gate. From
that moment the gate stopped meaning "do not blit stale woven pixels" and also
meant "do not repair the punch".

The punch happens regardless of the weave outcome: SkiaRenderer's difference clip
is armed on |inline3d_difference_clip_enabled_| alone (PrepareCanvas) — a
command-line switch read once at startup — during the page draw, strictly before
WeaveCompositedSurface runs and with no knowledge of whether the weave will land.
So on a missed frame the page IS punched and the repair IS skipped, and 2D
content above a tile vanishes for that frame.

Five exits behaved this way, not one: the liveness gate, the
`displayxr_shared_woven_mailbox_.IsZero()` "nothing woven yet" check, and the
three ProduceSkia / BeginScopedReadAccess / CreateSkImage failures on the woven
texture. The woven draw-back keeps its gate untouched; only the composite is
hoisted.

THE PIECE TO CARRY FORWARD
--------------------------
Above the mechanical hoist, the part that must survive into the follow-up is the
COUNTED LOG SPLIT. The pre-existing VLOG collapsed three distinguishable states
into one word, "skipped". The replacement separates them:

  * "over-plane PUBLISHED but NOT composited" — a plane WAS published, the page
    WAS punched, and the repair did NOT run. This is the bug state, and it is the
    only one that matters. Raised to LOG(ERROR), latched-decade throttled (first
    3, then 9/99/999/9999), and it carries plane size, window size, size_ok, and
    whether the representation and the read access were obtained — enough to tell
    a resize transient from a real refusal without another build.
  * a plane was published and WAS composited — the healthy path, VLOG.
  * NO plane was published this frame — nothing to repair, the page kept its own
    pixels. Also VLOG, and explicitly NOT the bug.

Grepping for `over-plane PUBLISHED but NOT composited` is the acceptance check
for the follow-up; before the fix it is the silent state, which is how this
survived as long as it did.

HOW TO USE THE HUNKS BELOW
--------------------------
The hunk headers are from the combined draft, so the `+` side line numbers assume
the mono half of 0112 has already been applied and the `-` side assumes main's
102-patch series. Both will have moved by the time the follow-up is authored, and
the Android fix will by then occupy the same region on its own arm. Treat this as
the specification and the reference implementation — re-derive the placement
against whatever the tree looks like, and generalize the Android fix rather than
adding a parallel one.
